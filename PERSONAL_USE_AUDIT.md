# PiTrac Easy-Connect personal-use audit

November 25, 2026 · Easy-Connect 0.9.1 · macOS arm64

**The local range works when it receives a shot. The main obstacle to playing at home is getting the assembled PiTrac to send that shot reliably.** Current upstream PiTrac and Easy-Connect disagree about where simulator connections and calibration live. The PC also reports some rejected shots as delivered. A GSPro purchase can wait until the standalone range passes the two-house test below.

The audited workspace is a source snapshot without Git metadata. The upstream comparison uses PiTrac commit `78f1de60fd21398f34d348f19f55e73029bc95f9`. The revision on the eventual Pi image matters. The bench used the upstream GSPro sender, an Easy-Connect enclosure with a simulated hardware backend, a paired desktop service, loopback sockets and Chrome. Physical cameras, radio association, the Windows installer and licensed GSPro remain unverified. [Upstream revision](https://github.com/PiTracLM/PiTrac/tree/78f1de60fd21398f34d348f19f55e73029bc95f9)

## What worked on the bench

| Check | Observed result |
|---|---|
| Discovery, pairing and incoming shots | The desktop discovered and paired with the simulated enclosure. After explicitly pointing the upstream sender at its relay, three synthetic swings crossed the paired link and produced three history entries and three range shots. Connection heartbeats added no extra swings. |
| Range without GSPro | The third swing arrived with the external simulator closed. Chrome showed all three shots and 172 yd of modeled carry for the last swing, supplied at 122 mph, 16.3° launch and 7,097 rpm backspin. The history retained its 122 mph ball speed and marked external delivery false. |
| Local history | The desktop writes the most recent 500 shots to disk. The range keeps 60 shots in memory. Closing the desktop or losing its Pi link during a swing leaves a gap in desktop capture. The relay does not replay missed swings into a later round. |
| Build and regression checks | The Pi update archive built and reported version 0.9.1. With the package installed in a Python 3.14.7 environment, the full suite passed 1,448 tests and skipped 21 documentation checks. The suite exercises the Wi-Fi state machine and relay using test hardware and simulator endpoints. |

Two environment details matter for reproduction. An initial source-only run had two updater subprocess import failures and one concurrent HTTP test connection reset. All three passed in the installed run. Separately, Apple's command-line Python 3.9.6 could not load Ed25519-capable libcrypto, yielding 3 failures and 89 setup errors, all with that cause. The passing command was `python -m pytest -n 4 -p no:cacheprovider -q --tb=short -rs` with the test environment first on PATH. The packaged desktop runtime and the Pi's system Python should each be checked on their target OS.

## Required work before relying on the range

1. **Configure the simulator PiTrac actually runs.** Easy-Connect writes four keys to `user_settings.json` and reads them back to decide that shot delivery works. Upstream imports that file only into an empty settings table, then runs enabled simulator instances from SQLite. With an existing settings row and no simulator instances, the bench produced a positive Easy-Connect relay check and **zero upstream targets**. In an empty database the migration created **two enabled targets**, GSPro and E6, and renamed the JSON. Easy-Connect then reported its relay check false. For the current image, manage one dedicated GSPro-format relay target through the PiTrac dashboard API at `/api/sims`. Read back its enabled state, endpoint and live connection. Reinstalling or restarting should reuse that target and preserve other user-configured destinations. The desktop should only forward a matching protocol to an external simulator. [Easy-Connect integration](src/pitrac_easy_connect/pi/pitrac.py) · [Upstream migration](https://github.com/PiTracLM/PiTrac/blob/78f1de60fd21398f34d348f19f55e73029bc95f9/Software/web-server/config_manager.py#L256) · [Upstream simulator API](https://github.com/PiTracLM/PiTrac/blob/78f1de60fd21398f34d348f19f55e73029bc95f9/Software/web-server/server.py#L304)

2. **Read hardware readiness from PiTrac and protect the calibration.** In both migration tests, upstream stored the two fixture camera matrices and Easy-Connect reported calibration missing. Its backup also reads the old JSON and skips an empty calibration section. Read upstream `/api/setup/status` for lens, position and applicable strobe calibration. Verify backup and restore against the active configuration on a spare card before relying on recovery. The Easy-Connect model downloader's hard-coded `ml_models` URL also returned 404. Current source uses `ml_assets`, and Easy-Connect's presence check accepts any file in each expected directory. Use PiTrac's model installation procedure for the chosen image and check that the selected model files load. [Backup implementation](src/pitrac_easy_connect/pi/backup.py) · [Model lookup](src/pitrac_easy_connect/pi/ml_models.py) · [Upstream setup status](https://github.com/PiTracLM/PiTrac/blob/78f1de60fd21398f34d348f19f55e73029bc95f9/Software/web-server/server.py#L1057) · [Upstream model directory](https://github.com/PiTracLM/PiTrac/tree/78f1de60fd21398f34d348f19f55e73029bc95f9/Software/LMSourceCode/ml_assets)

3. **Make a household move recoverable from the Windows PC.** The intended flow is to join the enclosure's owner-card Wi-Fi, open `http://10.42.0.1`, submit the new Wi-Fi details, switch the PC to that household network and reconnect Easy-Connect. The paired connection confirms the move within a 150-second window. The installer currently probes HTTP once after six seconds of active service, while normal wireless recovery can wait 45 seconds before the portal even binds. Poll for actual portal readiness through the boot recovery period. In a simulated reboot with a known network available, Direct Mode switched from the Pi hotspot back to the household network while its saved flag still said direct. Honor that setting at startup. Stage replacement credentials separately until confirmation so a retry on the same SSID cannot delete the last working profile. For a move with the same owner, use Wi-Fi setup. **Prepare for new owner** revokes pairings and can delete the PiTrac source clone. [Installer health check](packaging/pi/install.sh) · [Boot and rollback](src/pitrac_easy_connect/pi/wifi.py) · [Profile replacement](src/pitrac_easy_connect/pi/nmcli_backend.py) · [Ownership reset](src/pitrac_easy_connect/pi/service.py)

4. **Make Local Range a play mode.** The Range tab works after pairing, and the wizard offers “Finish later.” The software still tries an external simulator for incoming messages and reports a failure upstream with GSPro closed. Add a Local Range choice that accepts a measured swing, saves it once, displays the flight and reports local readiness independently. Preserve valid zero angles. The upstream sender supplied horizontal launch of exactly 0° on all three swings, and the current parser stored the direction as missing on all three. Keep missing spin distinguishable from measured zero when displaying a trajectory. 5. **Establish a Windows installation that can travel with the enclosure.** The advertised download site, source repository and Windows setup executable returned HTTP 404 to public requests during the audit. A private build is sufficient. Build and retain the Windows installer, matching Pi source and owner card offline. Exercise install, first launch, pairing, application restart and local history on the intended Windows machine. Public distribution and automatic updates can wait. For a Pi that also has Ethernet connected, fix the setup portal’s ownership check. The portal listens on all interfaces and grants owner access based on the Pi’s Wi-Fi hotspot state. Check the interface used by the request or require owner proof on the wired connection. This matters when onboarding a portable unit on a shared household LAN. ## GSPro recording

Easy-Connect forwards live shots to GSPro Open Connect on the same PC at `127.0.0.1:921`. The Pi-side loopback relay uses port **9210**. For a bench trial on an image with the current simulator dashboard, enable a single GSPro instance pointing to **127.0.0.1:9210 on the Pi**. This gives the local range a shot source even before the automatic setup is repaired. The same target can stay in place at the second house. [Upstream sender](https://github.com/PiTracLM/PiTrac/blob/78f1de60fd21398f34d348f19f55e73029bc95f9/Software/web-server/sims/gspro_sim.py) · [GSPro Open Connect specification](https://gsprogolf.com/GSProConnectV1.html)

In the bench trial, the external mock returned an explicit rejection, code 500. The upstream sender received that rejection, yet desktop history recorded the swing as delivered. The normal forwarding path treats any response as an acknowledgment and also marks a socket write delivered after silence. The wizard's generated test shot originates on the PC and bypasses the cameras, Pi relay and Wi-Fi link. Track local capture, external send, explicit acceptance or rejection, and unknown outcome separately. Exclude heartbeats and player-info messages from shot counts. Never automatically replay an ambiguous shot. When licensed GSPro is available, compare physical swings directly with its practice session. Historical Easy-Connect shots have no implemented import into a GSPro account. [Live forwarding](src/pitrac_easy_connect/companion/service.py) · [PC test shot](src/pitrac_easy_connect/companion/simulator_session.py) · [GSPro response semantics](https://gsprogolf.com/GSProConnectV1.html)

## Personal-use acceptance test

These are proposed pass criteria for the assembled system.

1. Record the Pi model, PiTrac revision, OS and app versions. Start from a working PiTrac installation. Confirm both cameras and the applicable strobe calibration in PiTrac's own dashboard. Hit a ball and verify speed, angles and spin there before diagnosing Easy-Connect.
2. At house A, install the desktop app on Windows and pair. Open Local Range, or the Range tab for the current manual trial. With GSPro closed, hit 20 balls across driver, iron and wedge. Reconcile each detected shot with one desktop history entry and one trajectory for each flyable shot. Compare mph, signed angles and rpm with the upstream values at their reported precision. Check the left/right direction with deliberately hit balls. Record camera misses separately from relay losses.
3. Move the powered-down enclosure and the same PC to a different SSID and DHCP subnet. Complete setup from the owner card, reconnect the PC and hit five balls. Return to house A and repeat after a cold boot. Pass when pairing, calibration and the loopback relay target survive, and no terminal command or IP edit is needed. Time power-on to first recorded shot at each house.
4. Try one wrong password, one unconfirmed switch and a reboot during a pending change on a backed-up test card. Confirm that the previous network or owner-card hotspot is reachable. Test same-name networks with different passwords if the two houses use that arrangement. Test router-free Direct Mode across reboot if it will be used. Close and reopen the desktop and verify that recorded history survives.
5. When GSPro is installed and licensed, open its practice range and hit ten measured balls. Compare GSPro's actual shot count and local history one-for-one. Disconnect and reconnect between swings. Check that the missed external delivery stays visible locally and that reconnecting adds zero strokes. [GSPro licensing and installation](https://gsprogolf.com/buy)

## Range realism and the first hole

Keep the existing flight model. It integrates drag and spin-induced lift, uses station pressure, temperature and humidity for air density, and produces a trajectory from measured launch data. Its six club benchmarks helped fit the coefficients. For example, a 167 mph driver at 10.9° and 2,686 rpm gave **266.6 yd** against the repository's 275 yd reference. The corresponding 7-iron case gave **168.7 yd** against 172 yd. Evaluate independent shots for carry, apex and lateral error before retuning. The landing model currently estimates rollout over flat ground, and a zero-launch putt produces no trajectory. [Flight implementation](src/pitrac_easy_connect/companion/flight.py) · [Benchmarks](tests/test_flight.py)

The smallest useful course extension is one offline par 3. Give it a tee, fairway, rough, green and cup. Persist the ball position, lie, stroke count and hole completion. A second swing must start where the first one stopped, and reopening the app should resume the hole. Add terrain intersection, surface-dependent bounce and roll, then a measured putting path or an explicit auto-putt rule. A test round should finish with GSPro closed. That single hole will expose the missing mechanics before more time goes into scenery or additional holes.
